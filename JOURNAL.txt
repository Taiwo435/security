### Explanation (for 1:1):

I started by defining a new audit category called REQUEST_AUDIT in AuditCategory.java — this is the label that appears in the JSON output to identify 
standalone audit events, replacing the misleading GRANTED_PRIVILEGES that the prototype used. Next, we added a `logRequestAudit(AuditMessage msg)` method to 
the AuditLog interface (AuditLog.java) and its implementations (AbstractAuditLog.java, NullAuditLog.java) so the system knows how to route our event to sinks. 
The core work was in AuditActionFilter.java — this is the lightweight filter that only runs in SSL-only and disabled modes (registered in OpenSearchSecurityPlugin.java 
via `getActionFilters()`). Inside its `apply()` method, we build an AuditMessage directly using data from the parameters: `request.remoteAddress()` for source IP, the `action` 
string for what was performed, `request.getClass().getSimpleName()` for request type, casting to `IndicesRequest` for target indices, and the `task` object for correlation IDs.
 The AuditMessage constructor automatically adds timestamp, node info, and cluster name from the ClusterService we inject.

The key tradeoff was: should we delegate message building to AbstractAuditLog (like existing categories do) or build it directly in AuditActionFilter? I/ Kiro initially tried the 
delegation approach, but discovered that AbstractAuditLog's helper methods (getRemoteAddress, getOrigin, getUser) pull from ThreadContext — which is empty in non-FGAC modes because 
the SecurityRequestHandler and transport interceptor that normally populate it are gated behind `!sslOnlyMode`. Rather than hacking ThreadContext population or changing 
OpenSearchSecurityPlugin's interceptor registration, we chose to build the event directly in AuditActionFilter using data available on the request object itself. This keeps the 
filter self-contained, doesn't affect FGAC mode at all, and avoids coupling to infrastructure that isn't active in our target modes.

Today we focused on testing and validation. First, we wrote unit tests for AuditActionFilter to verify that the event construction from Day 1 is correct. The tests mock ClusterService (for node/cluster info) and verify the full AuditMessage contains: category=REQUEST_AUDIT, the action string (e.g., "indices:data/read/search"), the request type class name (e.g., "SearchRequest"), target indices, remote source IP, and task ID for correlation. Then we tackled config validation. The issue: audit categories are configured by exclusion (you list what's disabled). In non-FGAC mode, 6 categories (AUTHENTICATED, FAILED_LOGIN, etc.) can never produce events because the authentication/authorization code that triggers them is entirely skipped. But if a user doesn't explicitly disable them, they appear "enabled" in config — misleading. Our solution: define AUTH_ONLY_CATEGORIES as a constant set in AuditCategory.java, then in initStandaloneAuditIfEnabled() (where we know we're in non-FGAC mode), read the user's disabled categories, subtract them from AUTH_ONLY_CATEGORIES, and if anything remains, log a single warning listing the categories that will never fire.

The key insight about why auth categories can't fire: the code path that would trigger them lives in SecurityFilter (the FGAC filter), auth backends, and the privilege evaluator — all of which are skipped by the early return in createComponents() when SSLConfig.isSslOnlyMode() is true. Our AuditActionFilter only ever creates REQUEST_AUDIT events. So the validation isn't preventing a bug — it's helping users understand their config is partially meaningless in their current mode.

Finally, we tackled a critical infrastructure issue: the `getSettings()` method in OpenSearchSecurityPlugin. This method registers which settings keys OpenSearch accepts in `opensearch.yml` — any unregistered key causes a startup crash ("unknown setting"). All audit settings (sink type, disabled categories, ignore users, webhook URLs, log4j config, etc.) were inside an `if (!SSLConfig.isSslOnlyMode())` block, meaning in SSL-only mode OpenSearch would reject any audit configuration. We moved the entire audit settings block (~380 lines) outside the gate so they're registered regardless of mode. Non-audit settings (Kerberos, RBAC, REST API, compliance) stay inside since they're genuinely FGAC-only. This unblocks users from actually configuring audit sinks in their `opensearch.yml` when running without full security.

For integration testing, we investigated the existing test framework (LocalCluster, AuditLogsRule, TestRuleAuditLogSink). The existing `audit()` builder method on LocalCluster can't be used for our tests because it writes audit config into the `.opendistro_security` index — which doesn't exist in SSL-only mode (no ConfigurationRepository, no EventBus, no index reader). Instead, we configure the audit sink directly via node settings (Map.of("plugins.security.audit.type", TestRuleAuditLogSink.class.getName())), which feeds into `initStandaloneAuditIfEnabled()` through `this.settings` just like a real `opensearch.yml` would. This lets us spin up a real SSL-only cluster, send requests, and assert on the actual REQUEST_AUDIT events captured by the test sink.

## SUMMARY — Standalone Audit Logging Implementation

### The Problem

OpenSearch's security plugin has three modes: FGAC (full auth + authz + audit), SSL-only (just TLS), and Disabled. Audit logging only worked in FGAC mode. Users running SSL-only or disabled mode had zero audit trail. Compliance frameworks (SOC2, HIPAA, PCI-DSS) require audit logs even without access control. Our goal: make audit logging work independently of the auth/authz stack.

### What We Built

A lightweight audit pipeline that captures every request in non-FGAC modes, without depending on authentication or authorization infrastructure.

### The Complete Flow (Startup → Event Capture)

#### Phase A: Startup

**`OpenSearchSecurityPlugin.java`** — the plugin entry point.

1. `createComponents()` detects SSL-only mode → calls `initStandaloneAuditIfEnabled()` → returns early (skips all FGAC setup)
2. `initStandaloneAuditIfEnabled()` reads `audit.type` from opensearch.yml → creates `AuditLogImpl` (initializes router + sink) → calls `setConfig(AuditConfig.from(settings))` to enable it
3. `getActionFilters()` registers `AuditActionFilter` in OpenSearch's action filter chain
4. `getSettings()` registers all audit settings outside the `!sslOnlyMode` gate so OpenSearch accepts them

#### Phase B: Runtime (Every Request)

**`AuditActionFilter.java`** — fires on every transport action.

5. `apply()` builds an `AuditMessage` from request data: source IP, action string, request type, target indices, task ID, node/cluster info
6. Calls `auditLog.logRequestAudit(msg)` → `AuditLogImpl.save(msg)` → `AuditMessageRouter.route(msg)` → sink writes it out

```
Client request → OpenSearch transport → ActionFilterChain → AuditActionFilter.apply()
    ├── Build AuditMessage (REQUEST_AUDIT)
    ├── auditLog.logRequestAudit(msg) → router → sink (log4j/index/webhook)
    └── chain.proceed() → request executes normally
```

### Files Modified (and Why)

| File | What We Did | Why |
|------|-------------|-----|
| `AuditCategory.java` | Added `REQUEST_AUDIT` enum; added `AUTH_ONLY_CATEGORIES` set | New category for non-FGAC events; categorization for validation |
| `AuditLog.java` | Added `logRequestAudit(AuditMessage msg)` | Interface method so the filter can send events to the pipeline |
| `AbstractAuditLog.java` | Implemented `logRequestAudit` as `save(msg)` | Routes the message to the sink |
| `NullAuditLog.java` | Added no-op `logRequestAudit` | Avoids NPE when no audit is configured |
| `AuditActionFilter.java` | **Created** — the lightweight filter | Builds and logs REQUEST_AUDIT events from request data |
| `OpenSearchSecurityPlugin.java` | Modified `initStandaloneAuditIfEnabled()`, `getActionFilters()`, `getSettings()` | Initialize audit in non-FGAC mode; register filter; ungate settings |
| `AuditActionFilterTest.java` | **Created** — unit test | Verifies event fields, category, chain continuation (mocked) |
| `StandaloneAuditLoggingTest.java` | **Created** — integration test | Real cluster in SSL-only mode: end-to-end event production |

### Key Architectural Decisions

1. Build events in AuditActionFilter, not AbstractAuditLog — ThreadContext is empty in non-FGAC modes
2. Call `setConfig()` explicitly — EventBus doesn't exist in SSL-only mode to trigger it
3. Register audit settings outside the gate — otherwise OpenSearch rejects yml config at startup
4. Warn but don't reject for auth categories — they can't fire anyway

    │

    │   ├── initStandaloneAuditIfEnabled() → AuditLogImpl + AuditActionFilter

### Explanation (for 1:1):

Today we focused on three gaps: remote address capture, disabled mode support, and comprehensive integration testing.

The remote address problem: when a user sends an HTTP request, OpenSearch receives it at the REST layer (where the TCP socket and client IP live), then internally converts it into a transport action. Our `AuditActionFilter` runs at the transport layer, but by then the IP is gone — `request.remoteAddress()` returns null. The fix: we added a REST handler wrapper that stores the IP in ThreadContext (a per-request key-value store) before the request continues. Our filter then reads it back from ThreadContext as a fallback. This uses the same mechanism and key that FGAC mode's `BackendRegistry` uses, keeping things consistent.

For disabled mode: the only missing piece was a call to `initStandaloneAuditIfEnabled()` in `createComponents()`. SSL-only mode already had it, but disabled mode's early return path skipped it entirely.

We also found and fixed a bug where `logRequestAudit()` called `save()` directly without checking `disabledTransportCategories`. Every other audit method goes through `checkTransportFilter()` which respects disabled categories — but our new method bypassed it. Now it checks before saving.

The integration tests validate the full pipeline end-to-end: field-level assertions (indices, node info, task ID, timestamp, action), edge cases (wildcard indices logged raw, cluster-level requests with no indices, bulk requests), and category suppression (separate cluster with REQUEST_AUDIT disabled produces zero events).

### Key learnings:
- `SSLRequestHelper.getSSLInfo()` already does the heavy lifting in FGAC mode — extracts certs, validates, extracts principal. But it takes a `SecurityRequest` wrapper, not a raw `RestRequest`. We accessed the SSLEngine directly instead.

### Key learnings:
