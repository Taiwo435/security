## Day 9 — Dynamic Configuration Architecture Notes (Week 4, Tuesday)

### Three config paths for audit settings:

1. **`audit.yml`** — stored in the `.opensearch_security` index, read dynamically by the security plugin (via `DynamicConfigModel`). This is the REST API-configurable path (`PUT /_plugins/_security/api/audit/config`). Controls the **FGAC audit** path (read by `AuditConfig`). Requires authentication to access.

2. **`opensearch.yml`** — node-level static config, read at startup only. Settings registered in `getSettings()` with `Property.NodeScope`. Used by ALL modes (FGAC, SSL-only, disabled).

3. **Cluster setting** — dynamic cluster state. Registered with `Property.Dynamic + Property.NodeScope`. Changed via `PUT _cluster/settings`. Works in ALL modes.

### Key insight:
- Dynamic settings via cluster settings should apply to ALL modes — not exclusive to standalone
- All modes read from `opensearch.yml` at startup, cluster settings override those values at runtime
- The goal for `plugins.security.audit.enabled` is to replace the `enabled: true` in `audit.yml` (security index) with a proper cluster setting that works universally
- Eventually: extract audit configuration OUT of the security index and into cluster settings, so it works in all modes without needing the REST API (which requires FGAC/auth)
- The security index path (`audit.yml`) is FGAC-only — cluster settings are universal

### Extension Points, Implementations, and Hooks:

| Extension Point (Interface) | Our Implementation (Class) | Hook (Method called by OpenSearch) |
|---|---|---|
| `ActionFilter` | `AuditActionFilter` | `apply()` |
| `TransportInterceptor` | `AuditTransportInterceptor` | `interceptHandler()` → `messageReceived()` |
| `IndexingOperationListener` | `ComplianceIndexingOperationListenerImpl` | `preIndex()`, `postIndex()`, `preDelete()`, `postDelete()` |

Pattern: OpenSearch defines the interface (extension point), we provide the class (implementation), OpenSearch calls our methods at the right time (hooks).

### Detailed Pipelines:

#### Document Write Tracking Pipeline:
```
Client: PUT my-index/_doc/1 {"name":"test"}
  │
  ▼
REST layer parses HTTP request
  │
  ▼
Action pipeline starts
  │
  ▼
AuditActionFilter.apply() fires → logs REQUEST_AUDIT event
  │
  ▼
Request reaches primary shard
  │
  ▼
ComplianceIndexingOperationListenerImpl.preIndex(shardId, index) fires
  → Checks: complianceConfig.writeHistoryEnabledForIndex("my-index")?
  → If write_log_diffs=true: fetches original doc from shard (for diff)
  → Stores original in ThreadLocal<Context>
  │
  ▼
Lucene writes the document to disk
  │
  ▼
ComplianceIndexingOperationListenerImpl.postIndex(shardId, index, result) fires
  → Checks: is logging enabled for this index?
  → Checks: did the write succeed? Is this the PRIMARY?
  → If write_log_diffs=true: retrieves original from ThreadLocal, computes diff
  → Calls auditLog.logDocumentWritten(shardId, previousContent, index, result)
  → Event logged as COMPLIANCE_DOC_WRITE category
  → Routed to configured sinks (Log4j, index, webhook, etc.)
```

Key points:
- preIndex/postIndex fire per DOCUMENT (not per request) — bulk of 1000 docs = 1000 hook calls
- Only fires on PRIMARY operations (not replicas — avoids double-counting)
- Skips the audit index itself (prevents self-referential logging)
- Config-driven: only logs if index matches write_watched_indices pattern

#### Transport Interception Pipeline:
```
Client sends: PUT my-index/_doc/1 {"name":"test"}
  │
  ▼
Node A receives HTTP request
  │
  ▼
AuditActionFilter.apply() fires on Node A → logs REQUEST_AUDIT
  │
  ▼
Node A determines: "primary shard is on Node B"
  │
  ▼
Node A sends transport message to Node B
  (action: "indices:data/write/index[p]")
  │
  ═══ Network (transport protocol) ═══
  │
  ▼
Node B receives transport message
  │
  ▼
AuditTransportInterceptor.interceptHandler() wrapper fires
  │
  ▼
messageReceived() on Node B:
  → Is action "internal:*" or "cluster:monitor/*"? → Skip, call actualHandler
  → Otherwise:
      → logTransportEvent(action, request, task)
          → Build AuditMessage (REQUEST_AUDIT category)
          → Add: action name, request type, remote address, task ID, user identity
          → auditLog.logRequestAudit(msg) → routes to sinks
      → actualHandler.messageReceived() → Node B executes the shard write
  │
  ▼
After primary write, Node B forwards replica to Node A
  (action: "indices:data/write/bulk[s][r]")
  │
  ═══ Network ═══
  │
  ▼
Node A receives replica transport message
  │
  ▼
AuditTransportInterceptor fires again on Node A
  → Logs the replica write as another REQUEST_AUDIT event
  → actualHandler proceeds with replica write
```

Key points:
- interceptHandler() is called ONCE per action at registration time (wraps the handler)
- messageReceived() fires on EVERY transport message for that action
- Only handler side (receiving node) — sender side not intercepted (avoids duplication)
- Non-blocking: try/catch around audit, actualHandler always proceeds
- Filters: internal:*, cluster:monitor/*, indices:monitor/* skipped (cluster noise)
- Chaining: OpenSearch chains multiple interceptors (ours + FGAC's auth interceptor in FGAC mode)
  - Last added wraps outermost → fires first when message arrives
  - Order doesn't matter since audit and auth are independent operations


 Unit tests prove the logic is correct. Integration tests prove the wiring works end-to-end. Both test the same production code, just from different levels.

 * if we wanted to make it configurable in the future, we could add a setting like plugins.security.audit.log_internal_actions: true that disables the hardcoded skip. But no one has asked for it, and
  FGAC has never offered it either — it would just create noise for 99.9% of users.
